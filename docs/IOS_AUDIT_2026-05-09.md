## A. Privacy Manifest (`ios/PrivacyInfo.xcprivacy`)

### A1 — Required Reason APIs declared — **PASS**
File: `ios/PrivacyInfo.xcprivacy:5-42`
UserDefaults (CA92.1), FileTimestamp (0A2A.1, 3B52.1, C617.1), DiskSpace (E174.1, 85F4.1), SystemBootTime (35F9.1) are all declared with valid reason codes. ActiveKeyboards is not used (no IME-related code), correctly omitted.

### A2 — `NSPrivacyTracking` value — **PASS**
File: `ios/PrivacyInfo.xcprivacy:45-46` → `<false/>`
Per `lib/subscription/useSubscription.tsx:40-44`, `initAttribution` is **stubbed to a no-op** in v1; real ATT path is commented out. Consequently the binary does not call `requestTrackingPermissionsAsync`, does not collect IDFA, and does not perform cross-app tracking. `NSPrivacyTracking=false` is therefore truthful **for the v1 binary**. See Followup: this assertion **must flip to `true`** the moment `initAttribution` is unstubbed (B2 below).

### A3 — `NSPrivacyTrackingDomains` — **PASS** (currently no tracking SDKs active)
Sentry is crash/perf telemetry, not cross-app tracking, so no domain entry is required while `NSPrivacyTracking=false`.

### A4 — `NSPrivacyCollectedDataTypes` empty — **MAJOR**
File: `ios/PrivacyInfo.xcprivacy:43-44` → `<array/>`
**Why it matters:** Apple's Privacy Manifest auditing tools and the App Privacy nutrition label expect this array to enumerate collected data types. The app collects:
- **Email** (Supabase Auth — `lib/supabase/auth.ts:351`, Apple Sign In requests EMAIL scope)
- **Name** (Apple Sign In requests FULL_NAME — `lib/supabase/auth.ts:352`; profile-setup screen)
- **User ID** (RevenueCat AppUserID, Supabase user.id, Sentry release tag)
- **Crash Data** (`@sentry/react-native` — `app/_layout.tsx:49`)
- **Performance Data** (Sentry traces — `tracesSampleRate: 0.05`)
- **Purchase History** (RevenueCat customerInfo, `purchase_history` Supabase table)
- **Other User Content** (capacity_logs, notes, tags — user-authored journal entries)

Empty array is a manifest mis-statement that will be flagged by `App Privacy Report` reconciliation in Xcode 16 and risks future App Review questions.

**Fix:** populate `NSPrivacyCollectedDataTypes` with each type, set `NSPrivacyCollectedDataTypeLinked=true` (linked to user identity via Supabase `auth.users.id`), `NSPrivacyCollectedDataTypeTracking=false` (none cross-app), and the appropriate `NSPrivacyCollectedDataTypePurposes` (`AppFunctionality`, `Analytics`, `Developer's Advertising or Marketing` is **not** used).
**Applied in Phase 3.** See diff in §A4-fix.

## B. Permission Usage Strings (`app.json` `ios.infoPlist`)

Current `app.json:31-34` infoPlist contains only `LSApplicationCategoryType` and `ITSAppUsesNonExemptEncryption`. **Zero usage strings.**

### B1 — `NSFaceIDUsageDescription` missing — **CRITICAL**
File: `lib/biometric/index.ts:228` calls `LocalAuthentication.authenticateAsync`. On iOS devices with Face ID this will trigger the system prompt; **without `NSFaceIDUsageDescription` iOS will reject or show generic "Wants to use Face ID" string at best, and recent iOS versions outright crash the app**.
**Why it matters:** App is shipping a biometric-gated vault/account flow. This is a guaranteed App Review reject if reproduced; it is a runtime crash on Face ID devices in the worst case.
**Fix:** Add `"NSFaceIDUsageDescription": "Orbital uses Face ID to unlock your private vault and protect sensitive actions."`
**Applied in Phase 3.**

### B2 — `NSUserTrackingUsageDescription` for ATT — **PASS (deferred)** with **MAJOR followup**
`expo-tracking-transparency` is in `package.json:69`, ATT call site exists in `lib/attribution/appleSearchAds.ts:50-72`, but it is **stubbed out** at `lib/subscription/useSubscription.tsx:43`. Because the binary never reaches `requestTrackingPermissionsAsync`, the string is not strictly required for v1.
**Why it still matters:** As soon as anyone unstubs `initAttribution`, the prompt will fire without a usage string and crash. To prevent regressions we add the string proactively (string presence alone does not trigger the prompt — only the API call does).
**Fix:** Add `"NSUserTrackingUsageDescription": "We use this only to measure how Apple Search Ads campaigns drive Orbital sign-ups, never to track you across other apps."` Coupled with re-enabling `initAttribution`, this becomes a complete ATT path. Until then the string is harmless — Apple does not force a prompt simply because the key is present.
**Applied in Phase 3** (string only; code change deferred).

### B3 — Other permission strings — **PASS**
Verified by import search on `expo-camera`, `expo-image-picker`, `expo-media-library`, `expo-av`, `expo-contacts`, `expo-calendar`, `expo-location`, `expo-music`, HealthKit, Microphone — **none are imported anywhere in `app/`, `lib/`, or `components/`**. The `Camera` symbol in `app/account.tsx:25` is the lucide-react-native icon, not a capture API. AvatarPicker uses pre-supplied avatars only.
Therefore: NSCamera, NSPhotoLibrary, NSMicrophone, NSContacts, NSCalendars, NSLocationWhenInUse, NSAppleMusic, NSHealthShare, NSHealthUpdate are all correctly absent. **No action needed unless those features are added.**

## D. Accessibility (WCAG 2.2 AA + iOS)

### D1 — Icon-only Pressables missing labels — **MAJOR**
- `components/TagSelector.tsx:72-84` — TagButton renders an icon and **no label text and no accessibilityLabel**. A VoiceOver user hears "Button" with zero context for any of the 6 tags.
- `components/HistoryItem.tsx:144-150` — Trash button is icon-only with no `accessibilityLabel`. VoiceOver says "Button"; user cannot tell it deletes the log.
- `components/CategorySelector.tsx:60-79` — Has a visible Text label, but no `accessibilityRole="button"` or `accessibilityState={{ selected }}`; VoiceOver does not announce the toggle state.
- `components/TimeRangeTabs.tsx:72-108` — Tab buttons have visible label text but lack `accessibilityRole="tab"` and `accessibilityState`.
- `app/(tabs)/_layout.tsx:52-75` — Tab.Screen icons have no `tabBarAccessibilityLabel` and `tabBarShowLabel:false` — VoiceOver users get "Tab, 1 of 3" with no name.

**Why it matters:** WCAG 2.2 SC 1.1.1 (Non-text Content), 4.1.2 (Name/Role/Value). Apple Accessibility Inspector will flag every one.

**Fix:** Apply `accessibilityRole`, `accessibilityLabel`, and `accessibilityState` per element. Low-risk fixes applied in Phase 3 to `TagSelector`, `HistoryItem` delete button, `CategorySelector`, `TimeRangeTabs`, and tab bar.

### D2 — Minimum touch target — **PASS** (with **MINOR** spot)

**Fix queued:** raise `hitSlop` to 12 in delete button.

### D3 — Reduce Motion / Increase Contrast — **MINOR**

For A+, observe the OS setting via `AccessibilityInfo` listener and default `settings.reduceMotion` from it.

### D4 — VoiceOver reading order on orb screen — **NOT VERIFIED** (manual)

### D5 — Color contrast — **PASS**

## F. Security

### F1 — Auth tokens in AsyncStorage, not Keychain — **MAJOR**
File: `lib/supabase/client.ts:35-56` — `customStorage` wraps `AsyncStorage` for the Supabase auth session. AsyncStorage on iOS is **not** stored in the iOS Keychain; it is plain-text in the app sandbox (encrypted at rest only by full-device encryption). On a jailbroken device or via a backup extraction, refresh tokens are recoverable.
**Why it matters:** Apple does not require Keychain, but A+ posture for any app handling personal health/journal data uses Keychain for auth credentials. The refresh token is the long-lived secret.
**Fix:** swap `customStorage` to a `expo-secure-store` adapter on native. **Blocked by Rule 1: no dependency changes without approval.** Logged as Followup.

### F2 — Service role key on client — **PASS**
Grep confirms `SUPABASE_SERVICE_ROLE_KEY` exists only in `api/*.ts` (Vercel server functions). `EXPO_PUBLIC_SUPABASE_ANON_KEY` is the only key bundled.

### F3 — ATS (NSAppTransportSecurity) — **PASS**
No `NSAllowsArbitraryLoads` or NSAppTransportSecurity overrides in `app.json` or anywhere in `ios/`. Default (HTTPS-only, TLS 1.2+) applies.

### F4 — Crypto — **PASS**
`expo-crypto` is used (`lib/supabase/auth.ts:341-346`) for SIWA nonce. No custom hashing or `Math.random()` for security purposes.

### F5 — Deep-link validation — **MINOR**
`app/_layout.tsx:347-366` accepts `orbital://log` and `orbital://reset-password` and `router.replace()`s. Both target known internal routes — no open-redirect. Good. Improvement opportunity: validate query parameters; currently `orbital://reset-password?token=...` would pass through to the `reset-password` screen which presumably reads the token. Confirm token verification on that screen — followup.

### F6 — Sentry PII — **PASS** (with **MINOR** caveat)
Sentry init (`app/_layout.tsx:49-133`) drops warning/info/debug, doesn't call `setUser({ email: ... })`. `beforeSend` doesn't scrub stack-trace strings, so a thrown `Error("Failed to load profile for user@example.com")` would leak. No such pattern was found in code, but consider adding an `event.exception` scrubber for emails.
